## 1. Owner requirements (261102)

> "password guessing is fine, maybe they will find a hit. I would like to have several passwords per page to allow for easter eggs."

> "We want to build this to facilitate multiple uses."

> "phrases also will unlock portions of a website. THink of threshold as the entry point to a labyrinth - depending upon what you enter different things could be allowed, could re-reoute you to another page etc... It should be designed in a way that is rather dynamic to facilitate playful experimentation later."

**Uses:** hidden text/HTML, hidden files, whole gated pages, site reactions, unlocking portions of a site, re-routing. **Decided:** eggs first, proven on this repo's demo; noesis may adopt it; the garden stays on staticrypt for now; `seal` is generic; weak phrases warn and are never refused; wrong phrases are silent by default, with an opt-in message.

## 2. Constraint check

| Constraint (Threshold project page [read]) | Result |
|---|---|
| #5 Events out, not page ownership | **Holds.** The element never navigates, injects, styles or plays anything. It emits; `open()` returns a `Blob`. Sealed page shells are the site's page. |
| #4 Consumer provides secrets; no global secret storage | **Holds at build time.** The optional key ring (§ 5) is browser-side storage, a real tension, accepted in Q1. |
| #3 "No persistence", #6 persistence waits for a second consumer | **Reopened** by "portions of a website". Opt-in and off by default (Q1). |
| Guiding: as simple as possible | New surface: 3 attributes (`sealed`, `remember`, `report-wrong`), 1 method (`addSealed`), 2 events (`threshold-error`, `tier-rejected`), 4 detail fields (`data`, `names`, `open`, `replayed`). No helper, no effect vocabulary, no text/file split. Plain mode unchanged. |

## 3. Threat model

Sealing hides content from anyone reading public output until they hold a phrase. Guessing is offline and unthrottled, which the owner accepts for eggs. It does not defend against a holder sharing a phrase, a compromised host, or a third-party script on the page (either captures the phrase). There is no revocation: old blobs on old deployments stay readable. Not for PII, financials or anything regulated (`web-access-control-patterns.md`).

Scale, at an assumed 10^5 guesses/s on a 10-GPU rig at 600k [unverified; scaled from a weak 1080 Ti figure [snippet]]: a dictionary two-word phrase falls in minutes, 3 Diceware words in about 54 days, 4 in about 1,200 years. One more Diceware word buys far more than any iteration count.

## 4. The unlock record and format

### Bundle

Versioned JSON, base64url fields. An unknown `v`, `kdf.alg` or `aead` is refused, never guessed. Unknown other fields are ignored, so the format can grow.

```json
{
  "v": 1,
  "id": "<16 random bytes>",
  "kdf": { "alg": "PBKDF2-SHA256", "iter": 600000, "salt": "<16 bytes>", "norm": "fold1" },
  "aead": "AES-256-GCM",
  "slots": [ { "iv": "<12 bytes>", "ct": "<AES-GCM(KEK, padded record)>" } ],
  "inline": [ { "pid": "<random>", "iv": "<12 bytes>", "ct": "<AES-GCM(CEK, bytes)>" } ]
}
```

### The record: what a slot decrypts to

**Recommendation: three fields, one of them opaque.**

```json
{
  "tier": "fox",
  "open": {
    "note": { "k": "<CEK>", "type": "text/html", "pid": "<inline id>" },
    "map":  { "k": "<CEK>", "type": "image/png", "pid": "<id>", "src": "/s/9f2c….sealed" }
  },
  "data": { "route": "/s/x7f3a…/", "theme": "moss", "sound": "bell", "step": 3 }
}
```

- **`tier`** is a name, passed out as today's `detail.tier`. Same event as plain mode.
- **`open`** maps site-chosen names to keys. Inline and URL-loaded payloads differ only in whether `src` is present. Type and URL are inside the record, so **URL-loaded payloads have no public index**: their count, size and location appear nowhere until a phrase opens them.
- **`data`** is any JSON, passed out untouched, with no schema and no reserved keys. A site inventing `sound` or `step` needs no release and no format change. Routes and every other effect live here, so they never appear in the source.

Records are padded to a 256-byte multiple; slots are shuffled; content keys are random per payload, never derived from a master. AAD (`wt1|s|<bundle id>`, `wt1|p|<pid>`) stops ciphertext being swapped; it is not a host-tamper defence.

| Layer | Does |
|---|---|
| **Element** | Loads bundles, derives once per distinct `kdf`, trial-decrypts slots, emits `tier-unlocked`, offers `open(name)`, optionally keeps the key ring. Nothing else. |
| **Site** | Everything visible: reveal, route, theme, sound, sequence. Reads `detail.data` and `detail.open`. |
| **`seal` default shell** | A small page for a whole gated page: inline element plus a handler that replaces the document. An ordinary consumer. |
| **Helper package** | None in v0.5 (Q3). |

```ts
interface TierUnlockedDetail {
  tier: TierName;
  data?: unknown;                        // sealed mode, untouched
  names?: string[];                      // keys of open
  open?(name: string): Promise<Blob>;    // inline or URL; lazy; Blob.type from the record
  replayed?: boolean;                    // came from the key ring, not typing
}
```

`<web-threshold sealed="#wt-bundle">` reads an inline JSON script; `sealed="/s/site.json"` fetches a same-origin URL (cross-origin is refused); `el.addSealed(bundle)` adds one at runtime.

**Modes never fall back.** Once sealed, `secrets` is never consulted; setting both emits `threshold-error` and refuses; a failed load never falls through to plain mode. **`detail` is visible to every script on the page**, since the event bubbles and is composed, so sealed pages carry no third-party scripts and `seal`'s shell inlines the element rather than using jsDelivr. `dist/web-threshold.js` is 4,067 bytes today [ran]; sealed code goes in a dynamic import or separate entry unless its measured cost is trivial.

### KDF and many phrases

**One derivation per attempt, then trial decrypts.** Trial cost on an M4 Max, Node 24.22, wrong key, 512-byte slots, median of 5 [ran]:

| Slots | 1 | 10 | 50 | 200 | 1,000 |
|---|---|---|---|---|---|
| Trial decrypts | <0.1 ms | 0.2 ms | 0.9 ms | 3.3 ms | 14 ms |

A 600k derivation takes 41 ms on the same machine [ran]. The derivation drives latency, not the slots. Phones are slower by an unmeasured factor [unverified].

**Iterations: 600,000**, OWASP's PBKDF2-HMAC-SHA256 figure, with "calculating a hash should take less than one second" as its general rule [read; undated page, addressing server password storage]. Real-phone latency is **not measured** and no published figure was found; my estimate is 100–800 ms [unverified]. Measure with a bench page at build; ship 600k if the slowest target phone stays under 1 s. `kdf.iter` is in the blob, so it can change without a format bump. `seal` refuses below 600,000; the element refuses above 5,000,000, so a bad bundle cannot hang a phone.

**Slot limits:** warn above 256, abort above 1,024. At about 400 bytes per slot [unverified estimate], 1,000 slots is 400 KB of poorly compressible JSON fetched by each page holding a door, so file size is the practical limit.

**What the count leaks:** array length is a public upper bound on doors. Off by default, so anyone can count the doors (Q4). A site can set `decoys` in its doors file: `seal` then pads with random slots of the same shape to the next multiple of that number. The element needs no code: a decoy is a slot that never decrypts. Nested doors (§ 6) are not visible at all.

### Shared salt with weak eggs beside a strong phrase

**Recommendation: one salt per `seal` run across its bundles.** Per-slot salt means N derivations per attempt, which many eggs rule out: 50 slots at an estimated 300 ms is 15 s per attempt on a phone [unverified].

- **What sharing costs.** One guess tests every slot at one derivation, so a dictionary run finds all weak eggs together. Slots are opaque, so with per-slot salts an attacker aiming at the strong phrase would pay N per guess; sharing removes that factor: log2(N) bits, 6 at N=64, under half a Diceware word.
- **A cracked egg exposes** that egg's phrase, `tier`, `data`, the payloads and URLs in its own record, and any nested bundle it opens.
- **It does not expose** any other phrase, slot or payload. KEKs come from independent phrases; content keys are random and appear only in records that declare them. A payload deliberately shared between doors is the only overlap.
- **Crypto cannot cover style.** A cracked egg teaches the theme and language of its author, sharpening the next dictionary. A strong phrase should be random words, not another line of the same poem.
- **Stronger content** goes in its own bundle with its own salt on the page that needs it, adding one derivation only there.

`seal` aborts if two doors share a phrase, since they would share a KEK and give an ambiguous result; that is a config check, not a strength check. IVs are random 96-bit, far below the 2^32 per-key limit at this scale.

### Wrong phrase stays silent; faults do not

All slots failing their tag is the only "wrong phrase" signal: no event, no text, input cleared at once. Opt-in `report-wrong` emits `tier-rejected` with no payload, and the site decides what to show. Malformed bundle, unsupported version, failed fetch or missing `crypto.subtle` emit `threshold-error` with `{ code }` plus `console.error`, and show the visitor nothing. On a slow phone a correct phrase leaves a gap that looks like failure, so the element sets `aria-busy` and a reflected `busy` attribute during derivation and drops further submits; visual treatment is the site's.

### Files

Binary payloads are always URL-loaded as raw bytes at random paths. Text is inline up to 64 KiB (a judgement call). WebCrypto's AES-GCM is one-shot, so plaintext and ciphertext both sit in phone memory. Proposed: warn above 2 MiB, abort above 10 MiB per file (Q5). Phone behaviour at those sizes and PDF viewing from `blob:` on iOS are [unverified].

## 5. Re-routing and portions of a site

### Re-routing

**Recommendation: a route is `data.route`, and the site's handler calls `location.assign`.** The element does not know about routes.

| Target | How | Hidden | Not hidden |
|---|---|---|---|
| Public page | `data.route: "/about/"` | That this phrase leads there | The page |
| Unlisted plain page | Long random path, unlinked | The URL, until revealed | Content, to anyone holding the URL: history, logs, shared links, previews |
| **Sealed page** | Random path + `seal` shell | URL and content | The shell's existence, if the URL is known |
| No page at all | `open()`, render in place, optional `pushState` | No URL to fetch | A reload needs the host to serve that path, so 404 or a hash route |

**What a static host cannot hide:** a URL that exists can be fetched, and any blob it serves is public. A random path is unguessable, not protected; a 200 versus a 404 confirms a guess; files stay on old deployments. A sealed page is protected by its phrase, not its path. Arriving at one without retyping needs the key ring; with `remember` off, the target shows its own door, which may be what a labyrinth wants. Token URLs stay out (constraint #3; they end up in history and shared links).

### Bundle scope

**Recommendation: one site-wide bundle by default, per-page inline bundles when a door belongs to one place.** Same format. In a site-wide `/s/site.json`, a record can name any payload, so a phrase on one page opens content on others, at one cacheable fetch per page. A per-page bundle gives true scope: the phrase is silent elsewhere. A page can use both; the same phrase in several active bundles emits one event per match.

### The key ring

**Opt-in `remember="session"`, off by default (Q1).**

- **Stored:** the KEK, as a non-extractable `CryptoKey` in IndexedDB, keyed by salt and iterations. `sessionStorage` holds only strings, so it could not keep the key non-extractable. Only a KEK that opened a slot is stored.
- **Session bound:** a random marker in `sessionStorage` must match or the ring is cleared, so "session" means this tab and tabs opened from it.
- **On load and on every `addSealed`:** the element tries ring KEKs against the slots and emits `tier-unlocked` with `replayed: true`. Sites have **one code path** and the event contract is unchanged, which fits #5. Handlers must tolerate repeats; a route handler ignores `replayed`.
- **New salt:** old KEKs stop matching, and doors need retyping. **Storage failure** (private mode, eviction) degrades to retyping, not a fault. Safari's storage behaviour is [unverified].

**What remains in the browser:** never the phrase. A KEK handle that any same-origin script can **use** but not export; non-extractable stops JS export, not forensics on a device profile. Content keys are not stored, but sit as raw bytes in JS memory while a record is used. Decrypted content stays wherever the site puts it: DOM, bfcache, `blob:` URLs until revoked.

## 6. Labyrinth depth

**Recommendation: a chain needs no format change.** A door that opens only after another is a **nested bundle**: door A's record names a payload of type `application/vnd.web-threshold.bundle+json`, and the site does:

```ts
el.addSealed(JSON.parse(await (await e.detail.open("deeper")).text()));
```

Ordering is cryptographic: B's slot is inside A's payload, so typing B first fails silently and an offline attacker cannot test B until they hold A. A strong outer door therefore protects weak inner eggs and their count. Replay works through § 5's retry on `addSealed`. Either/or is two slots holding the same key.

This relies only on payloads carrying a MIME type, unknown fields being ignored, and one derivation per distinct `kdf`. No field is reserved for it.

**Deliberately left out:** game state, attempt counters, timers, hints, ordering beyond nesting, AND-doors (two phrases at once), per-visitor state, server checks, token URLs, any route or effect vocabulary. Progress is not enforced beyond possessing keys: anyone given A and B has them. A site can build these on `data`, or new fields can be added later.

## 7. `seal` and the demo

### CLI

Node-only entry: `src/seal/`, `exports["./seal"]`, a `bin`; placement beside the policy CLI is settled at build time. A test asserts the browser bundle has no `node:` import.

```
web-threshold seal --doors doors.json --out dist [--shell shell.html] [--dry-run]
```

```json
{
  "payloads": { "note": { "from": "private/note.html", "type": "text/html" },
                "vault": { "from": "private/vault.html", "type": "text/html", "page": "s/x7f3a…/index.html" } },
  "doors": [ { "tier": "fox", "phrase": { "env": "EGG_FOX" }, "open": ["note"], "data": { "theme": "moss" } },
             { "tier": "keeper", "phrase": "literal phrase", "open": ["vault"], "data": { "route": "/s/x7f3a…/" } } ],
  "allowPublic": ["/about/"],
  "decoys": 16
}
```

**The doors file is a secret:** it holds phrases, routes and content pointers. It must sit outside `--out`, and `seal` warns if git tracks it (this repo is public [ran: `gh repo view`]). `--doors-env NAME` reads the same JSON from one env var for hosted builds (host size limits [unverified]). Phrases never go in argv; no `dotenv`.

**Order, exit non-zero on any fault:** validate → resolve phrases → seal to temp → read back → move into `--out` atomically → scan. Weak phrases only warn, by door name, never with the phrase or its length.

| Guard | Rule |
|---|---|
| Doors file | Inside `--out`, missing or unparseable aborts. Unknown payload name, empty phrase, unset env var and duplicate phrase abort. |
| `from` | A source inside `--out` aborts, unless `replace: true`, when it is overwritten and proved gone. |
| Read-back and isolation | Each door's phrase must open **exactly** its declared names, byte-identical. No record holds an undeclared key; no two payloads share a key. A random wrong phrase opens nothing. |
| Dist-wide scan | Search every text file in `--out`, normalised (strip tags, decode entities, unescape JSON, collapse whitespace, lowercase), for every 8-word run of each text payload (or the whole text if shorter), each `data` string of 6+ characters, each `page` path and each phrase. A hit aborts. A door's `hint: true` exempts its phrase, allowing a public clue; `allowPublic` exempts named strings. |
| Binary | A file in `--out` hashing the same as a sealed `from` aborts. |
| Coverage | Files scanned must equal files on disk. |
| Rerun | `--out` already holding a `seal` bundle aborts. |
| Floor and limits | Iterations below 600,000 and § 4's limits abort. |
| `--expect list` (optional) | Pages that must be sealed, compared both directions. |

Graphs, feeds and search indexes are the site's to strip before `seal`; the scan catches what it misses.

### Demo: the first consumer

Extends `index.html` with a second sealed page, built by a `seal` step into a gitignored directory, never the committed `dist/`. Its doors file is a public fixture, since the repo is public, so the proof concerns built output, not phrase secrecy (Q6). With no element or format change between items, it must show:

1. **Hidden text and file:** an egg reveals HTML; another opens an image through `blob:`.
2. **Whole gated page:** a sealed shell opening with its door.
3. **Site reaction:** `data.theme` changes the page, in demo code.
4. **New reaction, no release:** add `data.sound` by editing only the doors file and handler. This is the test of "playful experimentation".
5. **Portion of a site:** a phrase on page one reveals a section on page two with `remember="session"`, surviving a reload.
6. **Re-route:** to a sealed page, arriving open; with `remember` off, the target shows its door.
7. **Chain:** door B is silent until door A has opened.
8. **Many phrases:** at least 64 slots, timed on a real phone.
9. **Silence and opt-in:** wrong phrase silent; `report-wrong` shows a message. Plain demo still works.
10. **View source:** no phrase, route or egg text in built output, with one planted leak shown to abort the build.

## 8. Open owner decisions

**Decided by the owner, 261102:**
- **Q1, how long an unlock lasts:** opt-in `remember="session"`, default off, fresh salt per build. A `remember="<days>"` value can follow later with no format change.
- **Q2, phrase matching:** forgiving: trim, NFC, lowercase, collapse whitespace, fold smart quotes. Recorded as `kdf.norm: "fold1"`. Plain mode stays exact.
- **Q4, the door count:** no decoys for now, available as the `decoys` option in the doors file.

**Taken as recommended; say if not:**
- **Q3, reaction helper:** none yet. The demo's handler is the example, promoted once a second consumer wants it.
- **Q5, file limit:** 10 MiB per file, larger media out of scope, pending a phone test.
- **Q6, the demo:** local only, with public fixture phrases.

## 9. For the adversarial review

**Crypto**
- Shared salt among weak and strong phrases: is log2(N) right, including decoys and multi-target angles?
- Isolation: can a record reach another slot's keys by construction or a `seal` bug? Are AAD contexts unambiguous across nested bundles?
- Can decoys be told from real slots? What does folding (Q2) do to phrase space, and can `seal` and browsers normalise differently?
- Ring: same-origin use of a KEK, marker logic, replay after phrase rotation, bfcache.
- Raw CEK lifetime; plaintext in DOM, `blob:` URLs, service workers. Can a nested bundle force a costly derivation?

**Fail-closed**
- Can the scan miss a leak: short eggs, split markup, unhandled encodings, compressed outputs, source maps? Is a `data` string under 6 characters (route `/x/`) an acceptable hole?
- Do `allowPublic` or `hint` open more than intended? Is a warning enough for a tracked doors file?
- Can a build path skip `seal` and exit 0? Any path falling back to `secrets`, or replaying a slot it should not?
- Do `data` values reach a dangerous sink in the demo handler (`location.assign`, HTML insertion), teaching a bad pattern?
- Does `seal`'s log or error output ever carry plaintext or a phrase?

## 10. Tests that must exist

Each guard needs a planted fault it catches and a known-good input it passes (`memory/feedback/guards-fail-closed.md`). Canaries are nonsense tokens. Tests write only to temp directories.

- **Plaintext never in output:** canary, route, `data` string and phrase absent from all output in raw, HTML-escaped, JSON-escaped and tag-split forms; each also planted in a public page and required to abort. Phrases absent from logs and errors. JS-disabled load shows no content. `src` values absent from public JSON.
- **Wrong phrase silent:** no `tier-unlocked`, no `threshold-error`, no `tier-rejected` unless opted in and then without the phrase; no DOM change; input cleared. `constructor`, `__proto__`, `toString` silent in both modes. Double submit makes one attempt. A wrong phrase never enters the ring.
- **Record:** `data` comes out deep-equal, including odd shapes. Unknown fields are ignored. The element reads no `data` key.
- **Isolation matrix:** with N doors, each phrase opens exactly its declared names. A wrong key fails on each payload. Shared-payload doors both open it. Decoys never decrypt.
- **Depth and ring:** B fails before A, opens after `addSealed`, replays after reload. Key reads back `extractable: false`. Marker mismatch clears the ring. New salt stops matches without a fault. Off by default: nothing written to IndexedDB or `sessionStorage`. Storage failure degrades silently.
- **Faults:** malformed bundle, unknown `v`, iterations over ceiling, cross-origin URL, failed fetch, missing `crypto.subtle` emit `threshold-error` without unlocking.
- **Each guard fails on broken input** (one test per § 7 row), including `seal` stubbed to write plaintext, corrupted ciphertext, and a record with an undeclared key. A weak phrase warns and **succeeds**, printing neither phrase nor length.
- **Mutation:** `knowledge/tools/mutation-check.py`, no-op mutation first; removing each guard must fail a named test.
- **Compatibility:** mode A fails mode B's assertions; both set refuses; plain-mode tests pass unchanged; noesis builds against the new version. A v1 golden bundle decrypts in Node, WebKit, Chromium and Firefox, not only happy-dom.
- **Real use:** phone latency at 600k and 64+ slots recorded here; demo screenshots at phone and desktop (`knowledge/tools/ui-smoke.py --device both`), reviewed.
